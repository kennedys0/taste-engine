# Feedback and taste adaptation

## Feedback cycle

1. Restate the *specific* dissatisfaction in practical terms.
2. Identify likely dimensions: color, density, form, contrast, typography, spacing, surface, navigation, motion, copy.
3. Keep decisions the user liked unless they conflict with the revision.
4. Revise the smallest set of affected elements that solves the problem.
5. Recheck interaction, accessibility, and responsive integrity.
6. Ask for confirmation only if the unresolved choice materially affects the next step.

## Interpreting common feedback

- "Looks AI-generated" -> inspect repetitive card grids, generic headlines, excessive gradients, identical icon treatments, arbitrary decoration, and weak visual hierarchy. Do not assume the user hates all cards.
- "Too empty" -> inspect container widths, grouping, density, and underused viewport—not just reduce all spacing.
- "Not professional" -> inspect information quality, consistency, typography, hierarchy, loading states, and layout confidence.
- "Not my style" -> ask for the *highest-impact mismatch* or offer two concrete directions; do not pretend to know the user's taste.

## Persistence and consent

An in-conversation or in-session preference can inform the ongoing task. A reusable, cross-project preference file requires explicit opt-in. A user may authorize a project-level preference file without authorizing a global profile. Never silently edit an approved profile based on one ambiguous comment.

For proposed profile updates, identify what would be stored and whether it applies to one project or generally. Support correction and removal. Keep data limited to design preferences; do not store personal identity or sensitive inferred traits.
